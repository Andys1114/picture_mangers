# 前端在新目录整体重写，旧前端存档为 frontend-legacy（而非原地改造）

**状态**：已采纳（accepted，2026-07-26）

## 背景

收到"暗房霓虹"整套前端重设计交付稿（`docs/design/pm-gallery-redesign/`）：信息架构重组为前台 + 管理面板两层，视觉体系全部换新，覆盖桌面/移动/中间态 20+ 屏。设计稿 README 建议在现有 `frontend/` 里逐文件改造；但用户明确要求"旧前端标记废弃但不删除"。两者需要取舍。

## 决策

- 旧前端 `git mv frontend frontend-legacy` 整体存档：纯改名保留 git rename 追踪，README 加废弃横幅，不再维护但保持可手动运行；**不删除**。
- 新前端在 `frontend/` 从零重写，技术栈与模式不变（Next.js 15 App Router + TS + Tailwind + TanStack Query，自研 ui 组件、`lib/api.ts` 封装、hooks 目录），把 legacy 中仍适用的 api/hooks/配置移植过来。
- `dev.py` 及一切指向 `frontend/` 的工具链不动，天然指向新前端。

## 考虑过的替代方案

- **原地改造**（设计稿 README 的建议）：改动量看似小，但重设计实际替换了几乎所有用户可见界面（老组件仅 ~30 个文件，重叠可复用的只有 api/hooks/配置层），且原地改造后"旧前端"就不复存在，只能靠 git 历史找回，不满足"废弃但保留"的要求。被否。
- **双前端并存**（`frontend-v2/` 新建，稳定后再切换）：最稳妥，但目录名、启动脚本、文档都要区分两套，之后还要做一次切换动作；单用户自托管场景没有灰度需求，多出的复杂度买不到东西。被否。

## 后果

- 新前端从第一天起就是 `dev.py` 的默认目标，没有"半切换"状态；按子任务分阶段补齐功能期间，未完成的页面不挂导航入口。
- `frontend-legacy/` 作为随时可跑的参照物存在（对照行为、找回逻辑），代价是仓库里多一份不再演进的代码；接口层面后端只做增量改动，保证 legacy 始终能跑。
- 复用靠"移植"而非"共享"：legacy 与新前端零共享代码，改 legacy 无意义，一切修改只发生在新 `frontend/`。
- 收藏（星标/命名收藏夹）界面在重写第一版中整体暂缓，后端接口与领域概念保留（见父任务 `07-26-frontend-redesign` 决策 3）。
