# 连带关系在写入时算实（而非读时递归展开）

**状态**：已采纳（accepted）

## 背景

标签"连带"（implication）指：给图打了前因标签 A，系统自动补上后果标签 B（A→B）。问题是——连带关系可能在图片已经入库**之后**才建立，那么已有图上要不要补上后果、搜索时要不要做递归展开？

## 决策

连带关系在**写入时就算实**：打标签时（手动或抓取/导入）当场把前因的整条连带链（A→B→C）算出闭包，一次性写进 `post_tags`。`post_tags` 里存的永远是"展开后的完整标签集"。搜索时直接查 `post_tags`，**不做读时递归**。

配套两条不变量：
- 连带关系后加时，对现有打了前因的图做一次**回填**，补写后果，保住"post_tags 永远是完整展开集"这条不变量。
- 删除连带关系是**"黏"的**——不主动从老图上撤掉已写入的后果标签（那些标签可能是直接打的或别的连带带来的，撤起来歧义）。

## 考虑过的替代方案

- **读时递归展开**：`post_tags` 只记直接打的标签，搜索时用递归 CTE 把前因链展开后匹配。被否：写入侧只记事实、读侧负责派生，看似干净，但要每次搜索跑递归 CTE，且与计数（post_count）的懒重算耦合，漂移面更大。
- **写入时回填但不黏**（删连带时自动撤回）：被否：撤回歧义又昂贵（同一后果标签可能来自多条连带或直接打），不值得。

## 后果

- **搜索变简单**：`post_tags` 上做 AND 匹配即可，无需递归 CTE；递归 CTE 只剩一个用途——写入时算连带闭包（打标签 + 回填）。
- **计数永远准**：`Tag.post_count` = `post_tags` 中该标签的行数，永远反映有效集合，无需懒重算/脏标记。
- **删连带不撤标签**：用户需知道"删一条连带不会自动清理老图上已写入的后果"；如确需回收，做成手动管理操作。
- **防环仍需要**：算闭包本身会死循环，因此新建连带前必须做反向可达性检查（成环则 409 拒绝），闭包计算带已访问集合兜底。
- **存储略增**：`post_tags` 存的是展开集而非直接集，行数更多；单用户图库量级可接受。
